# 长任务上下文管理

模型上下文会丢失或压缩，**外部化的状态不会**。原则：重要信息写下来，不靠记忆。

## 1. 什么必须外部化

只写"不看就会做错"的东西：

- **目标与验收标准**（会随时间漂移）
- **硬约束**（不能改的接口、必须兼容的版本、权限边界）
- **已做的关键决定与理由**（防止反复推翻）
- **当前状态**（改到哪、哪些未验证）
- **已排除的方案**（防止重复试错）
- **产物位置**（文件、分支、链接）

不必写：过程性闲聊、已完成的琐碎步骤。

## 2. 写到哪

- 任务级状态：检查点/任务记录。
- 团队级共识：共享上下文（项目地图、接口约定、决策）。
- 代码级事实：代码与注释本身（最不会过期）。

## 3. 压缩前先摘要

接近上限时，按固定结构重写一遍状态，而不是让系统随机截断：

```text
目标 / 验收标准
硬约束
已完成（附证据）
关键决定
当前状态与下一步
已排除方案
未解决问题
```

摘要要能独立成立——新执行者只读它就能继续。

## 4. 恢复与交接

- 恢复时先读检查点，再读最近变更，**不要从头重来**。
- 交接时明确：已提交/已部署/仅本地/未验证的边界。
- 不假设对方知道之前的讨论；把必要背景写进交接内容。

## 5. 避免上下文污染

- 不复述大段已有内容，用引用（文件路径、条目 ID）。
- 一个事实只在一处维护，避免多处版本冲突。
- 发现旧记录与现状冲突时，更新或标注失效，而不是并存。

## 自检

```text
[ ] 换一个执行者接手，只读我的记录能否继续？
[ ] 关键决定是否附了理由？
[ ] 状态是否区分了"已完成/未验证/未开始"？
[ ] 是否有互相矛盾的记录？
```

## 红线

- 不把关键约束只留在对话里。
- 不用"如前所述"代替具体内容。
- 不在压缩后丢失验收标准。
