# 发布就绪检查

目标：回答一个问题——**现在发布，最坏会怎样，我们能不能退回来？**

## 1. 变更核对

- [ ] 变更清单完整（代码、配置、依赖、数据库、文档）。
- [ ] 没有未提交的临时调试代码、注释掉的逻辑、硬编码地址。
- [ ] 没有把密钥、令牌、内部地址带入仓库。
- [ ] 变更范围与需求一致，没有夹带无关改动。

## 2. 验证证据

- [ ] 相关测试通过，且有**实际执行记录**。
- [ ] 类型检查 / lint / 构建通过。
- [ ] 关键路径有集成或端到端验证。
- [ ] 未执行的检查已明确列出（不能默认通过）。

## 3. 兼容与影响

- [ ] 对外接口变更已分版本或加兼容层。
- [ ] 数据库变更向前兼容、可回填、可重跑。
- [ ] 配置默认值对旧部署安全。
- [ ] 依赖变更已评估。

## 4. 风险与回滚

- [ ] 列出本次发布的主要风险与触发条件。
- [ ] 回滚方案具体可执行（命令/步骤/负责人）。
- [ ] 数据类变更已备份，且确认备份可恢复。
- [ ] 有可观测手段确认发布后状态（日志/指标/健康检查）。

## 5. 结论

```text
结论：可发布 / 有条件发布 / 不可发布
阻塞项：<必须解决>
已知风险：<...>
回滚方案：<步骤>
发布后观察：<看什么指标，多久>
```

## 红线

- 不把"测试在本地过了"当成完整证据。
- 不在没有回滚方案时发布数据变更。
- 不隐瞒已知问题；有条件发布必须写明条件。
