# 变更影响分析

改之前先算清楚"会伤到谁"。**影响面不清楚时，先分析再动手。**

## 1. 界定改动

- 改的是内部实现，还是对外契约（公共函数、接口、数据结构、配置项、命令行参数）？
- 是新增、修改，还是删除？**删除和改签名风险最高。**
- 是否涉及持久化数据（表结构、迁移、序列化格式）？

## 2. 找出受影响范围

按依赖方向逐个排查：

1. **直接使用点**：搜索被改符号的所有引用。
2. **间接依赖**：调用链上游（谁调用了这些使用点）。
3. **数据侧**：读写该数据的代码、已有数据是否需要迁移。
4. **配置与文档**：默认值、示例配置、README、类型声明。
5. **测试**：哪些测试覆盖被改行为，哪些会因此失效。

只改内部实现时范围可缩小，但仍要确认没有隐含的对外行为变化。

## 3. 定风险等级

| 等级 | 特征 | 处理 |
| --- | --- | --- |
| 低 | 内部实现、无契约变化、有测试覆盖 | 跑相关测试即可 |
| 中 | 新增可选参数、行为边界变化 | 跑相关 + 相邻模块测试，更新文档 |
| 高 | 破坏公共接口、数据迁移、并发/安全相关 | 全量测试 + 构建，通知相关成员，必要时拆分 |

## 4. 输出

```text
改动：<一句话>
风险：低 / 中 / 高
受影响模块：<路径列表>
必须重跑的检查：<命令列表>
需要通知/协作：<成员或团队；无则写"无">
建议拆分：<如果要拆，怎么切；否则写"不需要">
```

## 5. 落地建议

- 高风险改动**拆成可独立验证的小步**，每步都能单独回滚。
- 破坏性改动优先提供兼容层（保留旧入口、加弃用提示），再分阶段移除。
- 影响跨团队时，把分析结论写入共享上下文，而不是只在本地记录。
