# 技术债分级

技术债不是"代码不好看"，而是**已经在拖慢或威胁交付的东西**。

## 1. 只记录有代价的债

每条债必须能说出具体代价：

- 改一个需求要动 N 个地方
- 每次发布都担心某个模块
- 新人上手要 X 天
- 同类缺陷反复出现
- 排查问题缺少必要信息

说不出代价的，是偏好，不是债。

## 2. 分级

```text
影响（高/中/低）× 触发频率（经常/偶尔/几乎不）
```

| 组合 | 处理 |
| --- | --- |
| 高影响 + 高频 | 立即排期，优先于新功能 |
| 高影响 + 低频 | 做好预案与监控，择机还 |
| 低影响 + 高频 | 顺手改，或加自动化 |
| 低影响 + 低频 | 记录，不投入 |

## 3. 偿还方式（从便宜到贵）

1. **顺手改**：本次改动正好经过的代码，小步改善。
2. **加护栏**：不改结构，先加测试、类型、校验，防止恶化。
3. **抽接口**：引入边界，把旧实现包起来，逐步替换。
4. **重写**：最后手段，必须有测试保护与回滚方案。

**默认不重写。** 重写通常低估成本、高估收益。

## 4. 与新功能的关系

- 债影响到当前需求时，**在同一轮里解决**（顺路改）。
- 债不影响当前需求时，单独排期，不夹带。
- 不把"重构"混进功能提交里，否则审查与回滚都困难。

## 5. 输出

```text
债务：<简述>
代价：<具体影响>
影响/频率：<高/中/低 × 经常/偶尔/几乎不>
建议方式：<顺手改 / 加护栏 / 抽接口 / 重写>
成本估计：<小/中/大>
不还的后果：<...>
```

## 红线

- 不因为"看着不舒服"就重构。
- 不在没有测试保护时做大结构调整。
- 不把技术债当成功能延期的通用理由。
- 不把重构与功能改动混在一次提交里。
