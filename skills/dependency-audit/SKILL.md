# 依赖评估

每个依赖都是**长期维护负担 + 供应链风险**。默认不引入。

## 1. 先问：真的需要吗

- 现有依赖或标准库能否覆盖？
- 自己实现的核心逻辑有多大？小于 ~100 行且无复杂边界时，自己写往往更可控。
- 这是一次性需求还是长期需求？

## 2. 评估维度

| 维度 | 要看什么 |
| --- | --- |
| 必要性 | 替代方案、自有实现成本 |
| 维护状况 | 最近发布、issue 响应、是否归档 |
| 体量与传递依赖 | 安装体积、拉入多少间接依赖 |
| 安全 | 已知漏洞、是否有安全公告渠道 |
| 许可 | 许可证是否与项目兼容 |
| 稳定性 | 主版本是否频繁破坏性变更 |
| 可替换性 | 是否被深度耦合，将来能否换掉 |

## 3. 引入时

- 固定版本（锁文件提交），不用浮动范围。
- 只引入需要的能力，避免整包副作用。
- 在边界封装：不要让第三方类型扩散到全项目。
- 记录引入理由（便于将来移除）。

## 4. 升级时

- 先读变更日志，找破坏性变更。
- 小版本逐步升，不跨多个主版本一次跳。
- 升级后跑全量测试与构建。
- 检查传递依赖是否也被动变化。

## 输出

```text
决定：引入 / 升级 / 移除 / 不引入
候选：<包与版本>
理由：<为什么>
风险：<维护性/安全/许可/体积>
替代方案：<自有实现或其他库>
验证：<测试与构建结果>
移除条件：<什么情况下可以去掉>
```

## 红线

- 不为了一个小功能引入大型框架。
- 不使用无维护、无许可说明的包。
- 不在未读变更日志的情况下跨主版本升级。
