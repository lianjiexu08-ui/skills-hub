# 任务编排

编排的核心不是"多派活"，而是**让依赖关系、状态流转和失败处理都是显式的**。

## 1. 拆分：按可独立交付的结果切

- 一个子任务 = 一个可独立验收的产出。
- 不要为了凑并行度把一件事硬拆成两半。
- 每个子任务写清：目标、验收标准、输入（依赖谁）、输出（交付什么）。

```text
| 子任务 | 负责角色 | 依赖 | 验收标准 |
| A 需求与验收标准 | 产品 | 无 | 每条验收标准可被命令或检查验证 |
| B 实现 | 工程 | A | 相关测试通过 |
| C 复核 | 审查 | B | 分级审查结论，无阻断项 |
```

## 2. 依赖与并行

- 只有真正无依赖的子任务才并行。
- 有依赖时，用显式依赖声明，不要靠"等一会儿再试"。
- 依赖链超过 3 层时，先确认是否拆得过细。

## 3. 分派

- 分派时给出：目标、验收标准、上下文（项目地图、相关决定）、权限边界。
- **只给必需权限**；不要为了省事扩大授权。
- 分派后记录关联 ID，便于追踪与回传。

## 4. 阻塞处理

按顺序判断：

1. **信息不足** → 先问，不要带着假设继续。
2. **依赖未完成** → 等待并显式记录等待原因，不空转轮询。
3. **执行失败** → 先做根因定位（见缺陷修复），再决定重试或换方案。
4. **需要人工决策/授权** → 明确升级，写清要决策什么、为什么、可选方案。

**不要无限重试，也不要用相同输入重复执行期待不同结果。**

## 5. 进度与检查点

- 阶段性保存检查点：目标、已完成、关键决定、产物位置、下一步。
- 检查点要能让**新的执行者**接着干，而不是只有原作者看得懂。
- 汇报进度时区分：已完成（有证据）/ 进行中 / 阻塞（原因）/ 未开始。

## 6. 收尾

- 汇总时核对**验收标准逐条是否满足**，而不是只看"子任务都跑完了"。
- 明确列出：已交付、未覆盖、已知风险、待人工确认项。
- 有跨团队协作时，把结论回传到发起方，而不是只留在执行方。

## 反模式

- 把"计划写完"当成"任务完成"。
- 子任务没有验收标准，靠模型自述"做完了"。
- 失败后不定位根因，直接换个说法重试。
- 所有子任务串行排队，浪费可并行空间。
- 授权范围随着任务推进不断扩大。
