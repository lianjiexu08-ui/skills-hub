# 代码问答

要求：**每一条结论都能指回具体代码**。不确定就说不确定。

## 1. 先定位，再回答

- 用符号搜索（函数名、类型名、路由、配置键）找到入口。
- 从入口向下读到关键分支，确认实际行为，而不是看名字猜。
- 需要跨模块时，跟着调用链走一段，确认数据形态变化。

## 2. 区分三种陈述

| 类型 | 标记方式 |
| --- | --- |
| 事实 | 引用 `文件:行` 或代码片段 |
| 推断 | 写"看起来/推测"，并说明依据 |
| 未知 | 直接说"没有找到"或"需要确认" |

**不要把推断写成事实。** 特别是："这里应该是为了…"——那是猜测。

## 3. 回答结构

```text
结论：<一句话>
依据：<文件:行 + 关键代码/调用链>
细节：<必要的数据流或分支说明>
注意：<边界、例外、已知限制>
未确认：<我没能确认的部分>
```

## 4. 常见问题的正确姿势

- **"在哪里处理 X"**：给出定义位置 + 至少一个调用点，说明触发条件。
- **"为什么这样写"**：先找注释、提交历史、决策记录；找不到就说"代码里没有说明"，不要编造动机。
- **"改了会影响什么"**：列出直接引用点，再说明间接影响（走变更影响分析）。
- **"这是什么架构"**：只在读完入口与主要模块后回答，避免只看目录名下结论。

## 5. 边界

- 不猜测未安装的依赖或未读到的文件的行为。
- 不把注释当实现（注释可能过期）。
- 不把测试当行为规范（测试也可能没覆盖）。
- 版本差异可能导致结论不同，注明读的是哪个版本/分支。

## 红线

- 不给出没有位置证据的实现描述。
- 不用"通常/一般"掩盖没有查证。
- 不臆测设计动机。
