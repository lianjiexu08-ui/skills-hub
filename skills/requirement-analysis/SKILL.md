# 需求澄清

目标：把"想要什么"变成"怎么证明做完了"。**没有验收标准的需求不能进入实现。**

## 1. 先分类信息

把掌握的信息分成三类，不要混在一起：

- **已确认**：用户明确说过的。
- **假设**：你推断的，需要标注。
- **待确认**：影响方案、但还没答案的。

## 2. 澄清关键问题（只问影响方案的）

按优先级，每轮只问最关键的少量问题：

1. **目标结果**：达成后，用户会看到什么变化？
2. **使用场景**：谁在什么情况下用？频率、规模？
3. **边界**：明确不做什么（比"要做什么"更能定范围）。
4. **约束**：兼容性、性能、安全、时限、必须沿用的技术栈。
5. **验收方式**：怎么检查？命令、界面、指标？

问题多到影响方案时，先问最阻塞的 1-3 个。

## 3. 写验收标准

每条验收标准必须**可被检查**，而不是"功能正常"：

```text
| # | 验收标准 | 检查方式 |
| 1 | 提交空表单显示错误提示 | 手动操作 / 组件测试 |
| 2 | 接口返回 400 且含字段名 | curl 断言 |
| 3 | 既有测试全部通过 | npm test |
```

不可检查的标准要改写或删除。

## 4. 输出

```text
目标：<一句话>
范围：做 <...>；不做 <...>
验收标准：<表格>
约束：<...>
待确认：<问题列表，标注是否阻塞>
```

## 红线

- 不把假设写成事实。
- 不用"用户应该会满意"当验收标准。
- 需求未清时不进入实现，也不假装"边做边确认"。
