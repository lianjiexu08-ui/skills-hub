# 缺陷修复

不靠猜测乱改。**先定位，再按可能性排序尝试，修好一个就停。**

## 1. 复现与定位

提方案前先收集：

1. **完整错误信息**：堆栈、错误码、失败输出。不要只看一行摘要。
2. **复现步骤**：什么操作触发，能否稳定复现。
3. **环境**：语言/依赖版本、平台、最近相关改动（`git log`、`git diff`）。
4. **定位范围**：读相关代码，追踪实际执行路径，缩小到具体位置。

信息不足时，先补充提问或自己查证。**禁止带着未验证的假设直接改代码。**

## 2. 列出修复方案（按副作用排序）

```text
| 优先级 | 方案 | 依据 | 风险 |
| 1 | <最小改动> | 为什么最可能命中根因 | 低 |
| 2 | <局部逻辑修改> | 依据 | 中 |
| 3 | <较大变更> | 依据 | 高 |
```

排序原则：配置/参数/边界判断 → 局部逻辑 → 依赖或架构变更 → 大范围重构。
**不要一上来就重构。**

## 3. 逐个尝试，成功即停

- 从优先级最高开始，**一次只试一个方案**，不叠加改动。
- 每个方案后用最小代价验证（跑相关测试或原复现步骤）。
- 解决了根因就停，不做顺手修改。
- 无效就回退该方案，记录"已排除 + 原因"，再试下一个。

## 4. 回归验证

- 跑与改动直接相关的测试、类型检查或构建，记录真实结果。
- 确认相关既有测试仍通过。
- 交付说明：根因、改了哪些文件、用了哪个方案、验证命令与结果、未覆盖的风险。

## 红线

- 没跑过的验证不得声称"已修复"。
- 不得用注释掉测试、跳过检查、吞掉异常来让报错消失。
- 根因不明时，交付"已定位到 X、已排除 Y/Z、建议下一步"，而不是假装修好。
