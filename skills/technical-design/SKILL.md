# 技术方案设计

目标：给出**能指导实现的最小方案**，不是写一篇架构文档。

## 1. 先确认输入

- 需求与验收标准是否明确？不明确先做需求澄清。
- 现有代码怎么做的？优先沿用既有模式，不另开一套。

## 2. 设计四件事

### 模块划分
- 改哪些文件/模块，每个负责什么。
- 边界清晰：谁拥有数据，谁只读。

### 数据流
- 从入口到输出的路径，关键状态存在哪里。
- 同步还是异步；失败时数据处于什么状态。

### 接口契约
- 函数签名 / API 形状 / 事件格式。
- 输入校验、错误码、向后兼容策略。

### 关键权衡
- 列出 1-3 个真正的取舍（如简单 vs 灵活，一致 vs 可用）。
- 每个给出选择与理由，以及被放弃方案的原因。

## 3. 方案对比（有多个候选时）

```text
| 方案 | 优点 | 缺点 | 改动面 | 风险 | 结论 |
```

选择原则：最小改动能达标 > 优雅但大改。**不要为了"以后可能用到"过度设计。**

## 4. 输出

```text
方案摘要：<3 行内>
改动点：<文件 → 改什么>
接口：<签名/格式>
权衡：<取舍与理由>
风险与回归范围：<需重跑的检查>
不做：<明确排除项>
```

## 红线

- 不引入未评估的新依赖；引入要说明替代方案。
- 不设计无法验证的方案；每步要能独立验收。
- 不隐藏风险；不确定的标注"待验证"。
