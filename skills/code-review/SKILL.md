# 代码审查

先取证，再判断。**不要只看改动的那几行就下结论。**

## 何时不用

- 纯问答、概念解释，没有实际代码变更。
- 只讨论命名、排版，不涉及可执行逻辑。
- 用户明确只要一句快速建议，不需要正式报告。

## 步骤

### 1. 确定审查范围

- 本地改动：默认审查未提交变更，或用户指定的文件/目录。
- 指定范围：用户给出的对比范围（base...head）或提交。

明确本次只审哪些文件，避免范围蔓延。

### 2. 取证

- 先看变更概览（`git status`、`git diff --stat`），确认改了哪些文件和规模。
- 阅读被改文件的**完整实现**，以及它的**调用方与被调方**。
- 行为变更时，找到相关测试，确认是否同步更新。
- 涉及公共接口时，搜索所有使用点，评估兼容性。

### 3. 预检门禁（先用规则，不靠感觉）

在人工判断前执行项目已有的自动化检查，把结果作为输入：

- 按项目类型运行：单元测试、类型检查、lint、构建。
- 命令不确定时，读 `package.json` scripts / `Makefile` / `go.mod` / `pyproject.toml`。
- **检查失败本身就是审查发现**，不要绕过或注释掉。

### 4. 分级输出

```text
## 结论：通过 / 通过（带建议） / 需修改

### 阻断（必须修复）
- [文件:行] 问题 → 为什么错 → 怎么改

### 建议（不阻断）
- [文件:行] 问题 → 影响 → 建议

### 已验证
- 自动化检查：命令 + 结果
- 测试覆盖：改动是否有对应测试
```

## 按风险优先级检查

1. **正确性**：逻辑错误、边界条件、空值、异常路径、并发竞态。
2. **安全**：注入、越权、密钥泄露、未校验输入、不可逆操作。
3. **兼容性**：破坏公共 API、改变既有行为、覆盖他人未提交修改。
4. **可维护性**：明显重复、过度复杂、违背项目既有风格。

## 红线

- 区分**事实**（代码确实错了）和**推断**（可能的风险），不夸大。
- 没读到的代码不断言没问题；没跑的检查不说通过。
- 审查阶段不擅自修改代码；阻断问题交给缺陷修复流程。
