# 可访问性检查

原则：**语义优先，ARIA 兜底**。错误的 ARIA 比没有 ARIA 更糟。

## 1. 结构语义

- 用原生元素表达语义：按钮用 `button`，链接用 `a`，标题按层级用 `h1`-`h6`。
- 可点击的 `div` 是反模式；必须用时要补角色、键盘与焦点。
- 页面有唯一主标题；标题层级不跳级。
- 表单控件必须有关联的标签（`label for` 或包裹）。

## 2. 键盘可达

逐项验证：

- [ ] 所有交互元素可用 Tab 到达，顺序符合视觉顺序。
- [ ] 焦点可见（不要全局去掉 outline）。
- [ ] 弹窗/菜单打开后焦点移入，关闭后回到触发元素。
- [ ] 焦点不会被困住，也不会跑到隐藏元素上。
- [ ] 自定义组件支持 Enter/Space 激活、Esc 关闭、方向键导航。

## 3. 屏幕阅读器

- 图片有意义的写 `alt`，纯装饰的用空 `alt`。
- 图标按钮必须有可读名称（可见文字或 `aria-label`）。
- 动态内容更新用合适的实时区域（`aria-live`），且不要滥用。
- 状态变化（展开/选中/错误）要能被读到，而不只靠颜色。

## 4. 视觉

- 文字对比度达到可读标准；不要只用颜色传达信息（错误、必填、状态）。
- 支持放大到 200% 不丢失内容与功能。
- 动画可关闭（尊重系统的减少动态偏好）。

## 5. ARIA 使用纪律

- 能用原生语义就不写 ARIA。
- 写了 `role` 就要实现对应的键盘行为与状态。
- `aria-*` 必须与实际状态同步；过期状态比缺失更误导。

## 6. 验证方式

- 只用键盘走完核心流程。
- 用浏览器无障碍树/审计工具检查名称、角色、对比度。
- 用屏幕阅读器抽查核心流程（至少：导航、表单提交、错误提示）。

## 输出

```text
问题：<页面/组件>
类型：<语义 / 键盘 / 朗读 / 视觉 / ARIA>
影响：<谁受影响、哪一步无法完成>
修复：<...>
验证：<键盘路径与工具结果>
```

## 红线

- 不用 ARIA 修补错误的 HTML 结构。
- 不移除焦点样式而不提供替代。
- 不只依赖颜色传达关键信息。
