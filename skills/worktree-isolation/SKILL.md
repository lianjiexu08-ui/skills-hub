# 工作树隔离

核心：**并行改动彼此不可见**。一个任务一个工作树，基线选错会污染范围。

## 1. 先确认身份

工作树通常由「仓库 + 路径」共同标识，例如 `repoId::/abs/path`。

- 复制**完整**标识，不要缩短成仓库 ID——仓库 ID 只标识仓库，不标识某个检出。
- 不同工具的选择器可能支持 `id:`、`path:`、`branch:`、`name:`；自动化时优先用完整 ID。

## 2. 选基线（最容易出错的一步）

| 场景 | 基线选择 |
| --- | --- |
| 独立新任务 | 仓库默认基线（不要基于当前特性分支） |
| 明确要求"从当前分支拉" | 当前分支 |
| 依赖未合并的前置改动 | 显式指定该分支，并记录依赖关系 |

**独立任务不要默认基于当前分支**——否则会无意中携带未完成的改动，导致"改着改着多出一堆别人的变更"。

## 3. 血缘 vs 基线是两件事

- **血缘**表示任务从属关系（子任务挂在父任务下），用于分组与追踪。
- **基线**决定代码从哪里开始。
- 把任务标为"独立"并不代表基线独立；两者要分别设置。

## 4. 创建后

- 确认工作树实际路径，后续命令都用它。
- 若工具自动打开了额外的空终端/空标签，确认它**确实未被使用**后再关闭，不要误关正在跑任务的会话。
- 记录：任务 → 工作树标识 → 分支 → 基线。

## 5. 并行规则

- 每个执行者只在自己的工作树内改动。
- 不跨工作树修改文件；需要共享的内容走提交或显式同步。
- 合并前确认：各自的工作树都有独立验证证据。

## 6. 清理

- 任务完成或放弃后移除工作树，避免残留分支与目录。
- 强制删除前确认：该工作树没有未提交改动，或改动已保留。
- 定期检查遗留工作树，防止磁盘与分支膨胀。

## 红线

- 不在共享检出上并行跑多个改动任务。
- 不基于当前特性分支创建独立任务。
- 不直接强制删除有未提交改动的工作树。
