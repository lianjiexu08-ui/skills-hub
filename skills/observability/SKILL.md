# 可观测性

判断标准只有一个：**只看这些输出，能不能回答"这个请求为什么失败"。**

## 1. 先问三个问题

- 出问题时，我需要知道**哪一次**请求出错？（关联 ID）
- 我需要知道它**走到哪一步**失败？（阶段/跨度）
- 我需要知道**失败原因**是什么？（错误码与上下文）

三个都答不上，就是埋点不足。

## 2. 日志

**要写**：请求开始/结束、关键分支、外部调用结果、降级与重试、错误与恢复。
**不要写**：密码、令牌、完整身份证/手机号、完整请求体中的敏感字段。

规则：

- **结构化**优先（字段而非拼接字符串），便于检索与聚合。
- **每个请求一个关联 ID**，贯穿所有日志与下游调用。
- 级别要有语义：`error` 只用于需要人处理的事；预期内的业务失败用 `warn`/`info`。
- 错误日志必须带：错误码、阶段、可复现的关键输入（脱敏后）。

## 3. 指标

- 请求类：请求量、错误率、延迟分位（p50/p95/p99）。**只看平均延迟会掩盖长尾。**
- 资源类：CPU、内存、连接数、队列长度、饱和度。
- 业务类：关键动作成功/失败数（比技术指标更早暴露问题）。
- 指标要有**标签**（接口、状态、租户），但避免高基数标签（用户 ID、原始 URL）。

## 4. 追踪

- 跨服务/跨异步任务传递 trace ID。
- 关键外部调用（数据库、HTTP、队列）各建一个跨度，记录耗时与结果。
- 异步与后台任务也要有独立可追踪的标识。

## 5. 告警

- 基于**症状**（错误率、延迟、饱和）而不是基于原因（CPU 高不一定影响用户）。
- 每条告警必须可行动：写清意味着什么、先看什么。
- 避免告警风暴：合并、去重、设阈值持续时间。

## 6. 自检

```text
[ ] 能否用一个 ID 拉出一次请求的完整链路？
[ ] 失败时日志是否包含阶段与错误码？
[ ] 是否有延迟分位而不是平均值？
[ ] 敏感字段是否已脱敏？
[ ] 每条告警是否都有人会处理？
```

## 红线

- 不记录密钥、令牌、完整个人数据。
- 不用 `error` 级别记录预期内的业务失败。
- 不加没有行动方案的告警。
- 不用高基数标签制造指标爆炸。
