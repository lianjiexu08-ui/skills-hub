# 工程交付流程

需求理解 → 方案设计 → 代码实现 → 代码审查 → 缺陷修复。

这条流程的价值是**每一步都有可检查的交付物**。跳过任何一步，后面都要用返工来还。

## 先判断当前在哪一步

| 现状 | 当前步骤 | 下一步 |
| --- | --- | --- |
| 只知道想要什么，验收标准不清 | 需求理解 | 补验收标准 |
| 需求清楚，但没想好怎么改 | 方案设计 | 写最小方案 |
| 方案清楚，还没动代码 | 代码实现 | 按模块实现 |
| 代码改完，还没复查 | 代码审查 | 复核 diff 并跑检查 |
| 有报错、测试失败、审查发现阻断问题 | 缺陷修复 | 复现并定位 |

不确定就从需求理解开始，不要直接改代码。

## 1. 需求理解

产出：**可检验的验收标准**。

- 明确目标结果、使用场景、约束（兼容性、风格、时间）。
- 把信息分成三类：**已确认**、**假设**、**待确认**。
- 假设不能当事实往下做；待确认项多到影响方案时，先问。

验收标准要能回答"怎么证明做完了"，例如"命令 X 输出 Y"而不是"功能正常"。

## 2. 方案设计

产出：**可指导实现的最小方案**。

- 先看项目已有做法，优先沿用现有技术栈和结构。
- 写清：改哪些模块、模块边界、关键权衡（给理由）。
- 改动面大时先做影响分析，确认回归范围。
- 只在必要时引入新依赖；引入要说明理由和替代方案。

## 3. 代码实现

产出：**可运行的改动**。

- 先读项目说明、构建配置，检查 `git status`，保留已有未提交修改。
- 陌生或大型项目，先用项目地图 Skill 建立认知。
- 按方案逐模块改，遵守现有风格；单一职责；校验外部输入；错误信息要有意义。
- 保持最小必要修改，不做顺手重构。

## 4. 代码审查

产出：**分级审查结论**。

用代码审查 Skill：先取证（读完整上下文、看调用链），再跑预检门禁（测试/类型检查/lint/构建），最后按"阻断 / 建议 / 已验证"分级输出。

阻断级问题进入缺陷修复。

## 5. 缺陷修复

产出：**根因 + 修复 + 回归证据**。

用缺陷修复 Skill：复现定位 → 列出按副作用排序的方案 → 逐个尝试、成功即停 → 回归验证。

## 贯穿全程的验证

- 运行与改动**直接相关**的测试、类型检查、lint 或构建，记录**实际命令和结果**。
- 命令不明时，读 `package.json` scripts、`Makefile`、`go.mod`、`pyproject.toml` 等确定。
- **没跑过的检查不得声称通过。**

## 交付说明模板

```text
改了什么：<文件与要点>
验证：<跑了哪些命令，结果如何；哪些没跑>
风险/限制：<未覆盖的场景、待确认项>
下一步建议：<如有>
```
