# 任务编排

编排的核心不是"多派活"，而是让**所有权、依赖和状态流转都是显式的**。

## 0. 先分清：交接还是受控分派

这两件事的后续义务完全不同，**先归类再动手**。

| 模式 | 含义 | 编排者的义务 |
| --- | --- | --- |
| **交接（handoff）** | 所有权转移，这件事不再归你 | 交付清楚即可，**不要**等待、轮询、监控 |
| **受控分派（dispatch）** | 你仍是协调者，对方是执行者 | 需要跟踪完成/失败、处理提问、汇总结果 |

判断规则：

- 用户说"交给 X 做"、"转给另一个团队"、"由 X 负责"→ 默认是**交接**。
- 用户说"盯着它"、"等结果"、"完成后汇总"、"协调这几个任务"→ **受控分派**。
- 分不清时，按交接处理（义务更少、更不容易出错）。

**不要**把交接包装成受控分派：那会让执行者误以为需要向你汇报，产生虚假的生命周期义务。
**也不要**把受控分派当成交接：没人收尾，任务会烂尾。

## 1. 拆分：按可独立交付的结果切

- 一个子任务 = 一个可独立验收的产出。
- 不为凑并行度硬拆。
- 每个子任务写清：目标、验收标准、依赖谁、交付什么。

```text
| 子任务 | 负责角色 | 依赖 | 验收标准 |
| A 需求与验收标准 | 产品 | 无 | 每条标准可被检查 |
| B 实现 | 工程 | A | 相关测试通过 |
| C 复核 | 审查 | B | 无阻断项 |
```

## 2. 依赖与并行

- 只有真正无依赖的子任务才并行。
- 依赖用**显式声明**，不靠"等一会儿再试"。
- 依赖链超过 3 层时，先确认是否拆得过细。

## 3. 分派

- 给出：目标、验收标准、上下文、权限边界、**期望的完成方式**（是否需要回报、回报什么）。
- 只给必需权限，不随任务推进扩大授权。
- 记录关联 ID，便于追踪与结果回传。

## 4. 阻塞与升级

按顺序判断：

1. **信息不足** → 先问，不要带假设继续。
2. **依赖未完成** → 显式记录等待原因，不空转轮询。
3. **执行失败** → 先定位根因，再决定重试或换方案。
4. **需要人工决策/授权/所有权不清** → 走**决策门**：写清要决定什么、为什么、可选方案、不决定的后果。

**不要无限重试，也不要用相同输入重复执行期待不同结果。**

## 5. 完成与复核的边界

- **复核类产出只报告发现，不授权改文件。** 复核完成后由协调者汇总，再决定谁来修。
- 若用户已指定"下一步由 X 做"，就**路由**给 X，不要自己接管。
- 完成汇报要区分：已完成（有证据）/ 进行中 / 阻塞（原因）/ 未开始。
- 不要声称"已编排"某工作，除非确实存在对应的任务与分派记录；工作是在体系外完成的，就如实说明。

## 6. 检查点

- 阶段性保存：目标、已完成、关键决定、产物位置、下一步。
- 检查点要让**新的执行者**能接着干，而不是只有原作者看得懂。

## 7. 收尾

- 逐条核对验收标准是否满足，而不是"子任务都跑完了"。
- 明确列出：已交付、未覆盖、已知风险、待人工确认项。
- 跨团队协作时把结论回传发起方，不只留在执行方。

## 反模式

- 把"计划写完"当成"任务完成"。
- 子任务没有验收标准，靠执行者自述"做完了"。
- 交接之后还在监控对方（越权）；或分派之后不管（烂尾）。
- 失败后不定位根因，换个说法重试。
- 所有子任务串行排队，浪费可并行空间。
- 授权范围随任务推进不断扩大。
