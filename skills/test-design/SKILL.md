# 测试设计

目标：测试要能**在实现出错时失败**。只覆盖正常路径的测试没有价值。

## 1. 找出必须覆盖的点

对每个改动列出：

- **正常路径**：最常见的一次调用。
- **边界**：空值、0、最大/最小、超长、重复调用。
- **错误路径**：非法输入、依赖失败、超时、权限不足。
- **状态转换**：多次操作后的状态（幂等、重试、并发）。
- **回归点**：这次修的缺陷，必须有能复现它的用例。

## 2. 选测试层级

| 层级 | 适合 | 成本 |
| --- | --- | --- |
| 单元 | 纯逻辑、边界、错误分支 | 低 |
| 集成 | 模块协作、真实 I/O、协议 | 中 |
| 端到端 | 关键用户路径 | 高 |

**优先单元覆盖逻辑，集成覆盖契约，端到端只覆盖少数关键路径。**

## 3. 写可维护的测试

- 一个测试只验证一件事；名字说明"在什么条件下期望什么"。
- 用固定输入和确定性断言，不依赖时间、网络、执行顺序。
- 断言**行为结果**，不断言内部实现细节。
- 测试数据就近构造，避免共享可变状态。

## 4. 验证测试本身

- 先让测试在**未修复**的代码上失败（证明它有效）。
- 再在修复后通过。
- 检查是否真的执行了断言（防止空跑）。

## 5. 输出

```text
覆盖点：<列表>
新增/修改测试：<文件与用例名>
未覆盖及原因：<...>
执行结果：<命令 + 通过/失败>
```

## 红线

- 不用"跑通了"代替"断言正确"。
- 不注释掉失败用例或放宽断言让它变绿。
- 不为凑覆盖率写没有断言的测试。
