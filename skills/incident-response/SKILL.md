# 线上故障响应

顺序不能错：**止血 → 确认 → 定位 → 修复 → 复盘**。
在压力下直接改代码定位根因，通常会让故障扩大。

## 1. 先分级

| 级别 | 判断 | 响应 |
| --- | --- | --- |
| 严重 | 核心功能不可用 / 数据损坏 | 立即止血，全员聚焦 |
| 较高 | 部分用户受影响 / 明显降级 | 尽快止血 |
| 一般 | 边缘功能异常，有绕过方式 | 正常排期修复 |

不确定时按更高级别处理。

## 2. 止血优先

按代价从低到高选择：

1. **回滚**最近一次发布（最快、最常见）。
2. **关闭开关**/降级有问题的功能。
3. **限流/熔断**保护下游。
4. **扩容**缓解容量问题。
5. **前置修复**（只改配置，不改代码）。

止血时**不要顺手改逻辑**，否则无法判断是止血生效还是改动生效。

## 3. 保留证据

止血过程中可能丢失现场，先做：

- 保存错误日志片段、指标截图、告警时间线。
- 记录变更历史：最近发布、配置变更、依赖升级、流量变化。
- **不要**急着清理磁盘、重启所有实例、清空队列。

## 4. 定位

- 确认影响范围：哪些接口、哪些用户、从何时开始。
- 找**时间相关性**：故障开始时间 vs 变更时间。
- 二分：按实例/版本/地域/租户切分，看是否只在某一片出现。
- 区分**触发因素**（导火索）和**根本原因**（为什么这么脆弱）。

## 5. 修复

- 修复后先用同一指标确认恢复，再宣布结束。
- 观察一个完整周期（如一个高峰）再关单。
- 记录实际执行的每一步，便于复盘。

## 6. 复盘（不追责）

```text
时间线：<何时发生、何时发现、何时止血、何时恢复>
影响：<用户/数据/时长>
直接原因：<触发因素>
根本原因：<为什么没有拦住>
已做：<止血与修复>
改进项：<每项有负责人与期限>
```

改进项要具体可验证（"加超时 3s"而不是"加强健壮性"）。

## 红线

- 不在未止血时深入排查根因。
- 不在故障中同时做多个变更。
- 不销毁现场证据。
- 不把复盘写成追责。
