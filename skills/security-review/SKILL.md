# 安全审查

目标：找出**可被利用**的问题，而不是罗列安全名词。

## 前提：先确认信任边界

- 哪些输入来自不可信来源（用户、外部 API、文件、环境变量）？
- 哪些操作有副作用（写文件、执行命令、发请求、改权限）？
- 谁能调用这段代码？权限边界在哪？

没有信任边界的分析都是空谈。

## 检查清单

### 输入
- 是否校验类型、长度、范围、格式？
- 路径拼接是否防目录穿越（`../`、绝对路径、符号链接）？
- 反序列化是否限制类型与大小？

### 执行
- 命令执行是否避免字符串拼接？参数是否转义？
- 是否有动态代码执行（eval、模板注入）？
- 文件写入是否限制在允许目录内？

### 认证与授权
- 是否每次都校验身份与权限，而不是只在前端隐藏？
- 是否存在越权（水平/垂直）？对象级权限是否检查？
- 令牌是否可撤销、有有效期？

### 数据与凭据
- 密钥是否硬编码、写日志、进 URL？
- 敏感数据是否加密存储、脱敏输出？
- SQL 是否参数化？

### 网络
- 外部请求是否校验目标地址（防 SSRF）？
- 是否校验响应大小与超时？
- 重定向是否受限？

## 输出

```text
| 严重度 | 位置 | 问题 | 可利用方式 | 修复建议 |
| 高 | file:line | ... | ... | ... |
```

只写**能从代码推出**的问题；不确定的标注"需验证"。
高风险问题应阻断发布。

## 红线

- 不因为"内网/只有自己用"就跳过检查。
- 不只报"建议加校验"，要指出具体缺哪一项校验。
- 不把安全声明（如只读标记、注释说明）当作事实证明。
