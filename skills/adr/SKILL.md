# 架构决策记录

目的：让**未来的人**理解决策当时的约束，而不是只看到结果。ADR 记录"为什么"，不记录"怎么实现"。

## 何时写

- 选择了会影响多个模块的结构方案。
- 在两个合理方案间做了取舍。
- 决定引入/移除重要依赖或基础设施。
- 决定接受某个已知技术债。

小改动不需要 ADR。

## 模板

```markdown
# ADR-<编号>：<决策标题>

- 状态：提议 / 已接受 / 已废弃（被 ADR-xxx 取代）
- 日期：YYYY-MM-DD

## 背景
当前面临的问题、约束、规模与已知事实。

## 决策
我们决定 <做什么>。

## 备选方案
| 方案 | 优点 | 缺点 | 未采用原因 |
| A | | | |
| B | | | |

## 后果
- 正面：<获得什么>
- 负面：<付出什么代价、接受什么限制>
- 后续：<需要跟进的事项、何时重新评估>

## 参考
相关代码、文档、讨论链接。
```

## 写法要求

- **事实与判断分开**：约束是事实，"更简单"是判断。
- **写清代价**：只写优点的 ADR 没有价值。
- **给重新评估的触发条件**：规模变化、依赖变更等。
- **编号单调递增，不修改历史 ADR**；被取代时改状态并指向新 ADR。

## 存放

放在仓库内的决策目录（如 `docs/adr/`），与代码一起版本化，便于审查时追溯。
