# 编写 Skill

Skill 是**给执行者的操作规程**，不是文档、不是宣传材料。判断标准：读完能直接照做，且做完能自检。

## 1. 先判断该不该写成 Skill

适合：

- 有稳定步骤、可重复使用的流程。
- 需要固定规则（校验、门禁、清单）来约束执行。
- 反复出现的同类任务，每次都要重新解释。

不适合：

- 一次性的具体任务（直接做）。
- 纯知识介绍（放文档）。
- 需要大量实时上下文才能决定的事。

## 2. 元数据

```yaml
---
name: <小写连字符，与目录名一致>
description: <做什么 + 什么时候用 + 触发关键词>
---
```

`description` 决定 Skill 会不会被正确触发，必须包含**用户可能说出的词**。

## 3. 正文结构

1. **何时用 / 何时不用** —— 防止误触发。
2. **步骤** —— 每步有输入和产出。
3. **判定规则** —— 用命令、检查、清单，而不是"感觉一下"。
4. **验证方式** —— 怎么确认这步真的完成。
5. **红线** —— 明确禁止的捷径。
6. **输出模板** —— 让结果结构一致、可审查。

## 4. 写法要求

- 能用规则判定的一律写规则（命令、正则、阈值）。
- 每个"必须"后面说明原因，否则容易被忽略。
- 抽象原则配一个具体例子。
- 控制在 60-200 行；细节拆到 `reference/` 按需读取。
- 不写死平台命令；只描述可移植的流程。

## 5. 自检

- [ ] 一个新执行者只读这份能完成任务。
- [ ] 有明确的"完成"判定，不靠自我评价。
- [ ] 包含失败与边界时的处理。
- [ ] 没有密钥、内网地址、个人信息。
- [ ] 与已有 Skill 不重复；重叠部分用引用而不是复制。
- [ ] 通过校验脚本（frontmatter、id 规范、禁用术语）。
