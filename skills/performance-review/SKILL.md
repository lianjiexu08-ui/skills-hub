# 性能审查

先测量，再优化。**没有数据支撑的优化通常是在制造复杂度。**

## 1. 定位瓶颈

- 有没有可用的指标/日志/耗时记录？没有先加最小埋点。
- 复现一个可量化的场景：输入规模、耗时、内存、QPS。
- 判断瓶颈类型：CPU、I/O、网络、内存、锁竞争、N+1 查询。

## 2. 常见问题清单

### 数据访问
- 循环里查数据库 / 发请求（N+1）。
- 缺少索引、全表扫描、一次拉取全量数据。
- 可以批量却逐条处理。

### 内存
- 一次性读入大文件或大响应。
- 缓存无上限、无过期。
- 持有不必要的大对象引用。

### 并发
- 串行等待可并行的 I/O。
- 锁粒度过大、在锁内做 I/O。
- 无界队列或无限制并发。

### 算法
- 嵌套循环、重复计算、重复序列化。

## 3. 优化顺序

1. **减少工作量**（少查一次、少传一份）——收益最大、风险最低。
2. **批量化/并行化**。
3. **加缓存**（必须有失效策略）。
4. **换算法或数据结构**。
5. 最后才考虑换技术栈。

## 4. 验证

- 优化前后用**同一场景**对比数据。
- 确认正确性测试仍通过。
- 确认没有引入资源泄漏、竞态或不一致。

## 输出

```text
瓶颈：<位置与证据>
原因：<为什么慢>
改动：<做了什么>
前后对比：<指标数据>
代价：<复杂度/内存/一致性上的取舍>
```

## 红线

- 不凭直觉说"这样更快"。
- 不为微优化牺牲可读性。
- 不引入无失效策略的缓存。
