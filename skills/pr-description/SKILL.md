# 变更说明

读者是**要审查这段代码的人**。目标是让他 2 分钟内知道：改了什么、为什么、怎么验证、有什么风险。

## 结构

```markdown
## 改了什么
<1-3 条，按重要性排序>

## 为什么
<问题背景或需求来源；关联 issue/任务 ID>

## 怎么做的
<关键实现选择，只写审查者需要知道的>

## 怎么验证
<具体命令 + 结果>
- `npm test` → 178 passed
- `npm run build` → success
- 手动：<步骤与预期>

## 风险与影响
<破坏性变更、性能影响、数据迁移、需要通知的模块>

## 未包含
<明确不在这轮做的事>
```

## 原则

- **结论先行**：第一段就说清核心改动。
- 具体而非笼统："修复了空指针"不如"当 `user` 为 null 时不再抛错，改为返回空列表"。
- 验证写**真实执行过的命令和结果**；没跑的不写。
- 大改动按逻辑分组，不要按文件罗列。
- 不粘贴大段 diff；用文件路径和行号定位。

## 反模式

- "优化代码""修复 bug"这种无法审查的描述。
- 只写做了什么，不写为什么。
- 把未验证的功能描述成"已完成"。
- 隐藏破坏性变更。
